Case study

BleedStop: a runtime cost and security guard for AI agents

A control plane for LLM, SMS and payment APIs, mapped to OWASP LLM10 (Unbounded Consumption). Apps call it before they spend money, and it answers ALLOW, LIMIT, CHALLENGE or DENY.

Source on GitHub Live demo Project site

Built end to end as a full stack and DevOps project. Stack: Node.js, Python, Postgres, Redis, Kubernetes. All numbers below were measured by me on one shared 8 vCPU Linux machine, where the load generator, load balancer and services all share the same hardware. Raw results are in the repository.

The problem

Once an agent can call tools and paid APIs, one prompt injection or one runaway loop can leak data or burn a budget.

BleedStop puts a decision in front of the spend. An application calls POST /decide before it pays for a call. Rules are deterministic and set per tenant, and budgets are enforced atomically across several instances through Redis.

What I built, end to end

Spend guard

Sits in front of LLM APIs and caps tokens and budget per request. In a test against a live model API, a capped request returned 64 output tokens instead of 2,618, which is 97.6% fewer.

Prompt injection detection

A DeBERTa classifier quantized to 8 bit so it also runs in the browser. On a held out test set it caught 77.5% of injections at a 5% false positive rate.

Atomic budgets

Redis enforces budgets across instances. In a correctness test of 2,000 concurrent calls against a $5 ceiling on 3 instances, overspend was $0.000.

Append only audit log

Every decision is written to a Postgres audit table where a trigger blocks UPDATE and DELETE, so decisions can be reviewed later but not edited.

Deployment

Docker Compose stack with 3 API replicas, Redis, Postgres and nginx, plus a Helm chart for Kubernetes with readiness and liveness probes, a PodDisruptionBudget, an HPA and graceful drain.

Observability and CI

Prometheus metrics, Grafana dashboards, alert rules and GitHub Actions CI. Node SDK with Express middleware, Python SDK, multi tenant YAML policy, and OpenTelemetry support.

Bugs that only appeared under load or failure

Running the system under stress found problems that unit tests did not. All of them are fixed. Examples:

  • Pods crash looping after loading 1.09 million rows at boot. Hydration is now skipped when Redis is authoritative, and otherwise capped to the top 50,000 rows by spend.
  • A Postgres writer that hung for good when the database went down. Connect and query timeouts fixed it.
  • Unhandled connection errors that crashed replicas when Postgres was stopped.
  • State kept per process, which split abuse signals across replicas behind a round robin load balancer. It now lives in Redis, and results match a single instance.

In total I found and fixed eight such bugs by running the stack, then kept the evidence in the repository.

What is honest to say about it

  • The golden set and the rules share an author, so the accuracy numbers are not field results.
  • Recall on the golden set is 48.0%. Precision is 100% with no benign false positives.
  • Not measured: NetworkPolicy enforcement, multi node or cloud clusters, Postgres high availability, and real provider latency or pricing.
