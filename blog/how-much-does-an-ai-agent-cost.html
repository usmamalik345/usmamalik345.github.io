How much does an AI agent cost to build and run? Real numbers from BleedStop

I am Osama Malik, an AI agent engineer at Onlinx Solutions in Islamabad. Every figure below is already on the BleedStop case study, in the BleedStop build post, in the public repository README, or on the Agent Receptionist case study. I am not adding a production bill or a savings figure those pages do not state. For a quote, see the hire page.

What cost means once an agent can spend

An AI agent is not only a model call. Once it can use tools, send SMS, or hit a payment API, cost has several parts: the tokens the model uses, the paid APIs those tools call, and what happens if a prompt injection or a runaway loop keeps calling them. I mapped that last risk to OWASP LLM10, Unbounded Consumption, when I built BleedStop.

BleedStop sits in front of the spend. An application calls POST /decide before it pays for a call, and gets back ALLOW, LIMIT, CHALLENGE or DENY from deterministic rules set per tenant. Redis holds the budget so several instances share one ceiling. A limit that lives only in a prompt is not a limit. A limit that lives in one process will split if you put more than one instance behind a load balancer. Those are the failure modes I was trying to close. If you are hiring someone to build an agent, I would start with that question. I wrote that up as a checklist for hiring an AI agent developer from Pakistan.

A token cap I actually measured

On the case study, a spend guard caps tokens and budget per request. In a test against a live model API, a capped request returned 64 output tokens instead of 2,618, which is 97.6% fewer.

The build post gives the README's extra detail on that same comparison. It was a small run on Groq's free tier, model openai/gpt-oss-20b, a streaming request for 1500 words, with a 64 token cap. Groq honoured the rewritten max_tokens, so BleedStop's own mid stream cut was not what stopped it. The README's reconciled cost at the policy rate fell from $0.0271 to $0.00151 per request. The actual bill was $0, because the tier was free. That is a cap test, not a monthly bill. It does not tell you what your production model, prompt, or traffic would cost.

The README also publishes a mock, and I will keep the label. A mock flood of 40 requests for 20,000 words, against an upstream that ignores max_tokens, cut 40 of 40 streams. At the README's policy rate of $0.01 per 1,000 tokens, with tokens approximated as characters divided by 4, that is $10.70 unprotected and $0.41 through the proxy. I am not calling that a customer saving. It is a mock. The case study lists real provider latency or pricing as not measured.

A $5 ceiling that several instances share

On the case study, a correctness test of 2,000 concurrent calls against a $5 ceiling on 3 instances overspent by $0.000. The same ceiling held behind a load balancer, with $0.000 overspend. That is about enforcement, not about the price of an agent. It does not say a real product should set its cap at $5, and it is not money saved for a customer. I do not have a production customer figure for money saved. Where the README prints a dollar amount, it is a policy rate or a local sample, and I have said which.

What it costs to run the guard itself

I cannot give you a cloud invoice for running BleedStop. I can give you the rates I measured on one shared 8 vCPU Linux machine, where the load generator, the load balancer and the services all share the same hardware. I treat those rates as a lower bound for a real cluster. Raw results are in usmamalik345/bleedstop.

TestResult
Docker Compose stack (3 API replicas, Redis, Postgres, nginx), one 8 vCPU machine5,433 decisions per second, p99 36.2 ms, 0 failed requests out of 60,000
3 instances behind a load balancer with Redis atomic budgets6,291 decisions per second, p99 31.9 ms, $0.000 overspend against a $5 ceiling
Kubernetes rolling restart of 6 pods under load0 failed requests out of 287,403
Postgres stopped for about 7 seconds under load86,071 requests, 0 failed, 0 ledger rows dropped
Capped request against a live model API64 output tokens instead of 2,618 (97.6% fewer)

The public demo at bleedstop-demo.vercel.app is not that cluster. The README is explicit: it runs on Vercel Hobby functions, in memory, with no Redis and no Postgres. The $5 cluster ceiling is not reliably enforced there. The measured rates come from the Compose and Kubernetes stack with Redis. The overhead estimate the README does stand behind is the mock upstream: npm run bench:openai, n=1000 calls that do not stream, added latency p50 1.53 ms and p99 1.86 ms.

One live question on Agent Receptionist

Agent Receptionist is a different project: a tool calling agent for appointment businesses, with cited RAG, policy routing and evals. The two demo businesses, a hotel and a dental practice, are fictional. The source is private and available on request.

On that case study, emergencies, opening hours and human handoff are routed by policy at zero tokens, so those turns never reach the model. One live public-URL check was 563 prompt tokens and 251 completion tokens, about $0.0002, with first token around 840 ms. The case study is clear: the latency and cost figures come from a handful of runs and one live check, and the suites show the engine behaves as designed, not how it would perform on a real business's traffic. I am not turning that single check into a cost per month.

What I will not claim

  • I do not publish rates, because scope changes the work a lot. There is no figure on this site for what it costs, in dollars, to build an AI agent.
  • I do not have a production customer figure for money saved.
  • Real provider latency or pricing was not measured as a benchmark on the BleedStop case study. The Groq run is one small free tier check in the README, not that missing benchmark.
  • The Vercel demo is not the cluster that produced 5,433 decisions per second or the rolling restart result.
  • The golden set and the rules share an author, so BleedStop's accuracy numbers are not field results. Recall on that set of 12,140 labeled requests is 48.0%. Precision is 100%, with no benign false positives.

If a page or a README already prints a dollar amount, I have quoted it as a policy rate, a mock, or a local sample. If a fact is not on those live pages, I have left it out.

For US, UK and Australian companies hiring from Pakistan

I work remotely from Islamabad, Pakistan, in Pakistan Time, PKT, which is UTC+5 and does not use daylight saving. I work with teams in the US, UK, Europe, Australia and the Gulf, and I am open to contracts and to full time remote roles.

Timezone overlap is often the first practical question. The full table is on the hire page timezone section, and I wrote a hiring checklist for teams that want an AI agent developer from Pakistan. In short: a 9:00 UK morning is 13:00 PKT in summer (BST, UTC+1) and 14:00 PKT in winter (GMT, UTC+0), so UK mornings fall inside my working day. A 9:00 US East Coast morning is 18:00 PKT in summer (EDT, UTC-4) and 19:00 PKT in winter (EST, UTC-5), which is evening for me. 9:00 PDT is 21:00 PKT and 9:00 PST is 22:00 PKT. For Australia, 9:00 PKT is 14:00 AEST or 15:00 AEDT in Sydney, so the overlap is an Australian afternoon and my morning.

If you are hiring from the US, the UK or Australia, the cost question should not stop at a day rate. I would also ask where the ceiling lives, what happens when it is hit, how the agent is evaluated, and how prompt injection is stopped before it can reach a tool or a paid API. The defence layers I use in BleedStop are in the prompt injection post. The job-specific pages are voice AI, RAG, LangGraph, AI chatbots, full stack and .NET.
