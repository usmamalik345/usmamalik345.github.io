A production point of sale and inventory platform

Osama Malik, an AI Agent Engineer in Islamabad, Pakistan (PKT, UTC+5), builds and maintains this production point of sale and inventory platform at Onlinx Solutions, where he has worked on-site since July 2024. It has paying customers. I have not published a public product name, a customer count, revenue or client names, so this page uses the plain description.

The problem this kind of system has to solve

A shop or warehouse cannot run on a spreadsheet once orders, payments and stock start moving at the same time. Staff at the counter need to take an order and a payment. Someone in the back needs to know what is actually on the shelf, not what last week's export said. Reserved stock has to expire if the sale does not complete. Invoices have to be generated without blocking the till. If those jobs live in separate tools that do not talk, you get a second set of books.

That is the problem space of a point of sale and inventory platform. I am describing the job the system is built to do, not a named customer's story, and not a metric I have not measured in public.

The stack

The backend is ASP.NET Core on .NET 8, written in C#, with MySQL and Dapper for data access. Authentication is JWT, with roles and permissions so staff only do what their role allows. Real time updates go over SignalR. Background workers handle imports, PDF invoices and reservation expiry, so those jobs do not have to finish inside the request that started them.

The frontend is Angular 19, in an Nx monorepo, with PrimeNG for the UI, Highcharts for dashboards, and barcode scanning for looking up and moving stock. Documents are stored on AWS S3. Document OCR uses AWS Textract. The app is shipped as Docker containers.

These are the parts I can name because they are already on this site. I am not adding a hosting region, a database size, or a performance number I have not published for this product.

What the system does

  • Orders and payments. The backend records sales and payments as part of the same platform, so a completed sale is not a row in one tool and a receipt in another.
  • Stock audits. Inventory can be checked and corrected, not only decremented when something is sold.
  • Roles, permissions and JWT auth. A cashier, a manager and a back-office user should not share one login with every action unlocked.
  • Background imports. Bulk data can be imported by a worker, so a large file does not have to block the request that uploaded it.
  • PDF invoices. Invoices are generated in the background, then stored with the rest of the documents.
  • Reservation expiry. Stock that is reserved for a sale that never completes does not stay reserved forever. A worker expires those reservations.
  • Real time sync over SignalR. The UI can stay current when orders, stock or payments change, without waiting for a full refresh.
  • Dashboards and barcode scanning. Highcharts is used for operational dashboards. Barcode scanning is used so staff can look up and move stock with a scanner. I am not publishing a particular KPI from those charts.
  • Documents and OCR. Files go to S3. Textract is used to read text from documents. I am not publishing an OCR accuracy rate.
